# 盲点監査 — 何が漏れていたか、なぜ漏れたか

- 2026-07-06。ユーザー指摘(カリキュラム設計の根拠が薄い)を受け、単発の穴埋めでなく**穴が出る構造そのもの**を診断する
- 目的: Takumiが「全体の骨(進め方のロジック)」を作るための材料を、網羅的かつ正直に提供する
- 結論の先出し: 私はこれを「UI・コンテンツ制作の仕事」として進めてきたが、実際は**最低5つの専門領域が交差するプロダクト**であり、私が厳格なリファレンス体系を持っていたのはそのうち1.5領域だけだった。すべての穴は「load-bearing(荷重を支える)な専門領域なのに、リファレンス層を用意しなかった領域」として説明できる。

---

## Part 1: 根本原因(なぜ同じ種類の穴が繰り返し出たか)

### 観測された私の癖
3回の指摘はすべて同じ形をしている:
1. UI: 「正しさ」の根拠はあったが「クオリティ(実トークン)」の根拠がなかった
2. UI: トークンはあったが「実在画面(スクショ)」というground truthがなかった
3. カリキュラム: UIの根拠はあったが「学習設計」の根拠がなかった(勘とBONO思想で断定)

### 根本原因(3層)
- **主因: 領域の見落とし。** 私は「目の前にある成果物」を高品質に磨くが、「この問題は本当はどの専門分野の総体なのか」を先に棚卸ししない。だから毎回、丸ごと1つの**リファレンス領域**が抜ける。穴はランダムではなく「私が荷重領域と認識しなかった分野」に必ず空く。
- **副因: 完全性チェックの不在。** 台帳→台本→Figma→計画と前へ速く作るが、「各分野の専門家なら何が足りないと言うか」という敵対的な棚卸しの工程を挟んでいない。
- **第三因: 可視・制作可能なものへの偏り。** 私はFigmaや台帳のような「作って見せられるもの」に引き寄せられ、学習の転移・需要の証拠・実行時のAI保証のような「作りにくい土台」を後回しにする。

### 対策の原理(UIで発見した方法の一般化)
UIは最終的に「①ルール(正しさ)+②クオリティ(実トークン)+⓪実物(ground truth)」の多層リファレンスで神の領域を狙えた。**この『ルール+クオリティ+実物』という3点セットを、荷重するすべての専門領域に対して用意する** —— これが穴を構造的に塞ぐ原理。カリキュラムなら「学習科学のルール+良い教材の実例+実際に学べたかの証拠」。

## Part 2: 穴の地図(漏れていた視点を領域別に)

重要度: ★★★=これが解けないとプロダクトの中核約束が崩れる / ★★=品質・信頼に直結 / ★=スケール時に効く
解く時期: [今] 骨作りと同時 / [v0前] プロトタイプ実装前 / [製品化前]

### G1. 学習設計・学習科学 ★★★ [今]
今回指摘された穴。加えてその下に複数の未対応がある:
- STEPの順序・「問う→型」・フェードを実ソースで裏づけていない(勘)
- **前提知識の定義がない**: 学習者が既に何を知っている前提か(デザイン語彙? Figma操作?)。前提が違えば同じ説明が刺さらない
- **誤概念モデルがない**: 初心者が持つ典型的な勘違い(例: 「装飾を足す=良くなる」)を、STEPが surface して直す設計になっているか
- **転移の理論がない**: お題01で学んだ型が、実務や別お題にどう転移するのか。企画が言う「型を知る→型を破る」の谷を渡す設計が未定義
- **定着(retention)の設計がない**: 1セッションやって終わり。間隔反復・想起練習など「学びが残る」仕掛けが無い

### G2. 評価・フィードバック設計 ★★★ [v0前]
- **開いた課題をAIがどう公正に評価するか**が未定義。STEP2/4は「正解が複数あり、理由の良し悪しを判定する」タスク。正誤判定でなく**論証の評価**で、これは本質的に難しいのに手つかず
- 決定論チェック(コントラスト等)は定義済みだが、**テイスト・判断の質**というフィードバックの本丸に方法がない(企画も認めていた宿題)
- 学習者が**自分の作品を模範と比べて自己評価できるか**という問題。初心者はそもそも良し悪しを見る目がないから習いに来る。自己評価の足場が要る
- 到達度の証拠が「1文の言語化」だけでは薄い。ルーブリック(観点別評価基準)が無い

### G3. 実行時のAIシステム設計(RAG・ガードレール・知覚)★★★ [v0前]
**最大の荷重穴。プロダクトの中核約束がここに集中しているのに最も手薄。**
- **AIが学習者のFigma作品をどう「見る」のか**が完全に未解決。「作りながら学ぶ+嘘のないフィードバック」は、AIが成果物を知覚できて初めて成立する。スクショを貼る? リンク? Vision? Figma API? ——ここを曖昧にしたまま全部を積んできた
- **実行時の出典ガード**が未実装・未設計。手動では subagent で「台帳内だけ」を守れたが、製品はLLMが生成する。台帳外の主張をどう機械的に弾くのか(企画の「検証ルール」は名前だけ)
- **会話の分岐**: 台本は一本道。実際の学習者の自由回答は無限に分岐する(的外れ・敵対的・空回答・gaming)。失敗モードの設計が無い
- **AIのペルソナ・口調**が未定義(BONOらしさは断定しただけ)

### G4. 需要・ユーザーリサーチの実行 ★★★ [今〜v0前]
- **まだ実ユーザーに一度も接触していない。** 全部が「初心者はこう」という仮説の上に建っている。H1(初心者は作る前で詰まる)すら未検証
- 対象(BONO初心者)とその痛みを**証拠なしで固定**した
- **競合を実際に使っていない**: 生成ツールが存在することは調べたが、自分で触って「判断力が育たない」隙間を体感していない

### G5. カリキュラム・アーキテクチャ(お題の連なり)★★ [今]
- 設計したのは**お題1つ**。だが「カリキュラム」は連なりを意味する。お題02は何で、なぜその順か。10〜30お題の学習アークの地図が無い
- お題選定の3条件は「品質が担保できるか」の基準で、「**技能がどう積み上がるか**」という学習順序の基準ではない

### G6. コンテンツ運用・保守・スケール ★★ [製品化前]
- 手作業で subagent を回して1お題作った。製品は多数のお題が要る。**お題→STEP変換が本当に自動化できるのか、毎回この手間がかかるのか**が未証明(=単位経済が不明)
- 台帳取得は難航した(JSレンダリング・取得失敗)。**製品スケールでのRAGソース獲得は本物の工学課題**。今回はその味見しかしていない
- **鮮度**: HIG/Materialは更新される。台帳を誰がどう保守するか

### G7. 動機・継続・行動設計 ★★ [v0前]
- DailyUIの真の死因は「フィードバック不在」だけでなく**人が飽きて辞めること**。フィードバックはレバーの1本で、動機・習慣化という別レバーに手をつけていない
- 「なぜここでは辞めないのか」の設計が無い(60分×継続の心理設計)

### G8. 事業アラインメント ★ [今、軽く]
- 企画には濃い事業分析(B2C/B2B/ポートフォリオ)があったのに、実作業は純粋なコンテンツ制作に漂流した。**今作っているものがどの事業モデルに最適化されているか**が宙に浮いている。BONO機能なら継続率、B2B研修なら網羅性と証明可能性、と設計判断が変わる

### G9. 法務・倫理 ★ [製品化前]
- 実在サービスのスクショ・他社トークンの商用利用(引用の範囲・出典・論評の要件)。README に注意は書いたが、製品化時の実運用ルールは未整備

| roadmap(Phase 0-6) | Phase 1を「コンテンツの核」としたが、G1/G2/G3という**土台の設計フェーズが欠落**。実質「UIコンテンツ制作」に矮小化していた |
| 仮説マップ | H1-H6は妥当だが**未検証のまま台本・Figmaを積んだ**(G4)。検証前に作り込むリスクを自分で冒した |

### 総括
現行計画は「作れるもの(UI・台帳・Figma)」に厚く、「作りにくい土台(学習設計・評価・実行時AI・需要証拠)」に薄い。**Part 1の第三因(可視・制作可能への偏り)が、計画そのものに刻まれている。**

## Part 4: これをどう活かすか(骨作りへの橋渡し)

Takumiが「全体の骨=進め方のロジック」を作る。その材料として、この監査から言える設計原理は1つ:

> **荷重するすべての専門領域(G1〜G9)に、UIと同じ『ルール+クオリティ実例+実物/証拠』の多層リファレンスと検証法を用意してから、作り込みに入る。**

骨を作る際の論点(Takが決める / 私が根拠を用意する):
- どの領域を「今解く」荷重穴と認定するか(私の推奨: G3・G1・G4 の3つが最優先)
- 各領域のリファレンスを、UI台帳と同じ厳格さ(実ソース取得・引用・出典必須)で作るか
- 「検証前に作り込まない」を今後の規律にするか(=土台設計→小さく検証→作り込み、の順を固定)

私の役割: 骨(ロジック)が決まったら、各領域のリファレンス台帳と設計を、UIでやったのと同じ「記憶で書かない・実ソース引用」の作法で作る。

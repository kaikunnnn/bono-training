# ダメなUIを4段階で直す — 配色の基本を1画面で試す（本文の下書き）

- 図の指定は 【図: …】 で書く。画像は bad-ui/color-bad-ui.html の各版（詳細を開いた状態・ピンなし）
- 数値は bad-ui/contrast.py の出力。出典IDは docs/10-ledger の台帳

---

## 導入

タスク管理アプリの1画面を用意しました。左にプロジェクトのメニュー、右側にタスクの一覧と、行を押すと開く詳細があります。この画面には、配色のよくあるミスを14個入れています。どれも「わざと壊した」ほど派手なものではなく、急いで作るとつい入ってしまう程度のものです。

【図: ダメUIの全体（詳細を開いた状態）】

この記事では、この画面を4段階で直していきます。1つの段階は、配色の記事の1つの章に当たります。

- 段階1　A 色は役割で決める
- 段階2　B 色の量を絞る
- 段階3　D 意味を持つ色
- 段階4　C 数値で確かめる

記事の章の順（A・B・C・D）と比べると、最後の2つが入れ替わっています。数値で確かめるのを最後に1回だけにしたかったからです。先に数値を合わせてから状態の色を作り直すと、同じ文字の濃さを2回直すことになります。色を決めきってから、最後にまとめて計算で確かめる順にしました。

直すのは色だけです。ボタンや行の大きさと位置は、どの段階でも変えていません。各段階で変わる場所も、1か所につき1回だけにしています。前の段階と見比べれば、その章の基本で何が変わったのかだけが見える作りです。

---

## 段階1　A 色は役割で決める（項目1・2・4）

最初に決めるのは「何色にするか」ではなく「その色に何をさせるか」です。押せる所、今いる場所、通知の数のように、色の役割を先に決めてから色を当てはめます。

【図: ダメUI → 段階1 の全体比較】

### 青は「押せる所」の色にする（項目1）

ダメUIでは、同じ青がいろいろな所に使われていました。押せるボタンとリンクだけでなく、押せないロゴ、プロジェクトの印、選択中のタブ、進み具合のバーまで青です。これでは、青い物を見ても押せるのかどうかが分かりません。

段階1では、押せる青を #1552E0 の1色に決め、「新規タスク」とリンクだけに使いました。ロゴ、進み具合のバー、選択中のタブは、青をやめて濃い文字色（#1f2328）にしています。プロジェクトの印はピンクにしました。

【図: 拡大 — ロゴ・タブ・バーの青が消えたところ】

Apple のガイドラインは、同じ色で別々の意味を表さないよう求めていて、ブランド色で押せる物を示しているなら、押せない文字に同じ色を使うと混乱する、という例を挙げています（CL-01）。NN/g も、押せない文字をリンクと同じ色にしないよう書いています（CL-02・CL-03）。

この段階では、「招待」と「タスクを削除」はまだ前の青のままです。この2つは段階2でボタンとしての強さを直すので、ここで色を変えると、同じボタンの色を2回変えることになります。

### 選択中のナビは、ボタンと張り合わせない（項目2）

ダメUIでは、サイドバーで今いる「新サイト公開」が、青で大きく塗りつぶされていました。右上の「新規タスク」も同じ青の塗りなので、2つが同じ強さで目に入ります。

段階1では、選択中を淡いニュートラルの塗り（#e6eaef）にして、左に濃い線、文字を太字にしました。大きな色の面がなくなったので、押すためのボタンとは見た目がはっきり分かれます。

【図: 拡大 — サイドバーの選択中】

ここは会社によって考え方が分かれます。Apple と Fluent は、今いる場所もブランド色で示す例を出しています（CL-21・CL-95）。一方で Material 3・Atlassian・Spectrum は、選択中を主ボタンと別の色にしています（CL-96・CL-64・CL-99・CL-97）。Spectrum は「ナビの選択中が、主な操作のボタンと注目を取り合っている」図を悪い例に挙げています（CL-97・CL-98）。この画面では Spectrum に近い形を選びました。ブランド色を使う場合でも、大きく塗りつぶさず、文字の色や細い線にとどめるのがおすすめです。

### 通知の数は、塗りと文字の組で決める（項目4）

ダメUIの通知の数字は、橙の塗りに白い文字でした。比率は2.85:1で、本文の基準の4.5:1に届きません。塗りの色だけを決めて、上に載せる文字の色を一緒に考えなかったときに起きるミスです。

段階1では、赤の塗りに白い文字の組にしました（5.36:1）。赤はエラーと削除の色ですが、通知の数字のバッジは、多くのアプリが赤にしている慣習に合わせた例外にしています。慣習に合わせるか、ブランドの色にするかも、会社によって分かれる所です。Apple のガイドラインは、未読のバッジをアクセント色の使い道に挙げています（CL-21）。

## 段階2　B 色の量を絞る（項目5・6・7・18）

次は、色を出す場所を減らします。色は足すほど目立つのではなく、出す場所を絞るほど、見せたい物が目立ちます。

【図: 段階1 → 段階2 の全体比較】

### 画面の大半はニュートラルで組む（項目5）

ダメUIのアプリの地は #EEF3FF でした。白に近い色ですが、並べると青みがはっきり分かります。

段階2では、地を #eff2f5、カードを #f6f8fa にしました。どちらも GitHub の Primer の色です。純粋なグレーではなく、ほんの少し青みが入っています。

ここで、「画面はグレーで組む」と覚えると、少し言い過ぎになります。Google の Material 3 は、背景用のグレーの段階を、ブランドの色と同じ色相のまま彩度だけをごく低くして作っています（CL-102）。実際に Gmail の背景は #F8FAFD で、うっすら青いグレーです。

色みの強さ（CIELAB の彩度）を計算すると、違いが数字で見えます。Gmail の背景は1.7、Primer の淡い地は1.2、この画面のアフターの地は1.9です。ダメUIの地は6.4で、Gmail の約4倍あります。ブランドの色みを少し混ぜるのはよく、ダメなのは、見て分かるほど色みが強く、押せる青と同じ系統に見えることだと考えています。

Carbon・Atlassian・Polaris などは、画面の大半をニュートラルで組み、色は操作と意味に取っておく、と書いています（CL-16・CL-17・CL-19・CL-20）。

### 目立つ色のボタンは1画面に1つ（項目6）

ダメUIでは、「招待」「新規タスク」「タスクを削除」の3つが同じ青の塗りでした。どれがこの画面の主役なのか分かりません。

段階2では、青の塗りを「新規タスク」だけにして、「招待」は白地に枠のボタンにしました。詳細を開いたときは、「変更を保存」も青の塗りになるので、多くても2つです。

【図: 拡大 — 見出しの右のボタン】

### 削除は赤くする（項目7）

ダメUIでは、「タスクを削除」と、確認の画面の「削除する」が、いつもの青い主ボタンでした。取り消せない操作が、ふだんの「保存」と同じ見た目になっています。

段階2では、詳細の「タスクを削除」を白地に赤い文字と枠に、確認の「削除する」を赤の塗りにしました。最初の入口は控えめに、最後の確認ははっきりと、という強さの分け方です。

### 押せるボタンをグレーにしない（項目18）

ダメUIの「変更を保存」と確認の「キャンセル」は、グレーの塗りに薄いグレーの文字でした。押せない状態のボタンと見分けがつきません。

段階2では、「変更を保存」を青の塗りに、「キャンセル」と「複製」を白地に枠のボタンにしました。この項目は、配色の記事では章E「操作の状態」に入っていますが、ボタンの強さの話なので、この段階で直しています。

【図: 拡大 — 詳細の下のボタンと確認の画面】

## 段階3　D 意味を持つ色（項目11・12・13・14）

ここからは、エラー・成功・注意のように、意味を伝える色を整えます。

【図: 段階2 → 段階3 の全体比較】

### 状態の色は借りてくる（項目11）

ダメUIの状態の札は、淡い地に明るい文字でした。「レビュー待ち」は淡い黄色に黄色の文字で、比率は1.79:1しかありません。

段階3では、Primer の「淡い地と濃い文字の組」をそのまま借りました（CL-100）。

- 未着手: グレー
- 進行中: 情報の青
- レビュー待ち: 黄
- 差し戻し: 橙
- 完了: 緑

どれも4.5:1以上です。進行中の青は淡い札なので、塗りの青いボタンとは別の物に見えます。

【図: 拡大 — 状態の札】

自分で色を選ぶと、明るさの調整に時間がかかり、画面ごとにばらつきます。デザインシステムの組をそのまま使えば、組み合わせの比率も最初から確かめられています。

### 注意には強さの段階がある（項目12）

ダメUIでは、画面の一番上のメンテナンスのお知らせと、詳細の入力エラーが、同じ赤い見た目でした。知らせておけばよい情報と、すぐ直してほしいエラーが同じ強さに見えます。

段階3では、お知らせを黄色の地にふつうの文字（アイコンだけ黄土色）にしました。赤は入力エラーと期限切れの日付だけに残しています。状態の札の「差し戻し」も、エラーの赤ではなく一段強い注意の橙です。

### 状態の色を飾りに使わない（項目13）

ダメUIでは、「デザイン」タグが成功の緑、「企画」タグが注意の黄、「NEW」がエラーの赤でした。プロジェクトの印も緑と黄です。これでは、緑を見たときに「完了」なのか「デザイン」なのかが分かりません。

段階3では、タグと NEW を、地を塗らない枠だけのラベルにしました。プロジェクトの印は、見分けるための色なので色は残し、状態の色・押せる青・紫を避けて、青緑とオリーブにしています。

印を全部グレーにする案もありましたが、それでは印を置く意味がなくなります。大事なのは色をなくすことではなく、意味のある色と重ならない色を選ぶことです。

### 色だけで伝えない（項目14）

ダメUIでは、優先度は色の点だけ、必須の項目はラベルの赤だけ、期限切れは日付の赤だけでした。色の区別がつきにくい人や、白黒で印刷したときには伝わりません。

段階3では、次の3つを足しました。

- 優先度: 棒の数で段階が分かるアイコンと、「高・中・低」の文字
- 必須の項目: 「必須」の文字
- 期限切れ: 日付の右の「!」のアイコン

優先度の付け方は、Linear に合わせています（CL-101）。色を付けるのは「高」の橙だけで、中と低はグレーです。タスク管理のアプリは、優先度に色を付けるのが普通です。ただ、Jira や Asana のように全段階に色を付ける製品と、Linear のように一番上だけに付ける製品に分かれています。

【図: 拡大 — 優先度・期限切れ・必須】

## 段階4　C 数値で確かめる（項目8・9・10）＝アフター

最後に、見やすさを感覚ではなく数字で確かめます。

【図: 段階3 → 段階4 の全体比較】

### 本文は背景と4.5:1以上（項目8）

ここまで直しても、サブの文字・説明文・選ばれていないタブは、薄いグレー（#A1A1AA）のままでした。カードの地との比率は2.46:1です。

段階4では、Primer のサブ文字の色（#59636e）にしました。カードの地とは5.74:1、アプリの地とは5.44:1です。WCAG は、本文の文字を背景と4.5:1以上にするよう求めています（F-01・CL-28）。

### 入力欄の枠やアイコンも3:1以上（項目9）

入力欄の枠は #EBEBEB で、白に対して1.19:1でした。どこに入力欄があるのか、ほとんど見えません。

段階4では、枠を #818b98（3.45:1）、検索のアイコンやアカウントの「…」を #59636e（6.11:1）にしました。WCAG は、入力欄の枠のように「見えないと操作できない物」を隣の色と3:1以上にするよう求めています（F-03・CL-33）。区切り線のような飾りの線は、薄いままでかまいません。

### 文中のリンクには下線（項目10）

詳細の「記入ルールはこちら」は、色だけでリンクだと示していました。

段階4で下線を引きました。WCAG の技法は、下線のない文中リンクには周りの文字と3:1以上の差を求め、下線を消して色の違いだけにするのを失敗例に挙げています（CL-37・CL-38）。リンクの色は、段階1で押せる青にそろえてあります。

【図: 拡大 — 詳細の入力欄とリンク】

## まとめ

【図: ダメUI と アフター の全体比較】

14個のミスを、配色の記事の4つの章に沿って直しました。振り返ると、段階ごとに見ている物が違います。

- 段階1: 色の役割
- 段階2: 色の量
- 段階3: 意味のある色
- 段階4: 数値

どの段階でも、ボタンや行の位置は動かしていません。それでも、画面の印象は段階ごとにはっきり変わります。

この記事で何度か書いたように、選択中の色、背景の色み、優先度や通知の色は、会社によって正解が分かれています。1つの正解を探すより、「この色は何の役割か」「意味のある色と重なっていないか」「数値で足りているか」の順に確かめていくのがおすすめです。

なお、この画面は配色のほかにも、ナビの階層、絞り込みのタブの位置、見出しの右のボタンの数などを直しています。これらは配色の話ではないので、どの段階にも同じ形で入れ、この記事では扱っていません。

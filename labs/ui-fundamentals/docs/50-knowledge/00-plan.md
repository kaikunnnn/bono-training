## 3. 記事の構成案 — 「UIの余白で知るべき9個」

### Xの決定
**X = 9個**を推奨。根拠: (a) 8px/近接/ターゲット/行送り/画面マージン/密度/レスポンシブ/最小限/反例、の9つで初心者に必要な余白概念を過不足なく覆える。(b) ミラーの法則(S-09)的に7±2の上限内。(c) 10分読了(約4,000〜6,000字)に収まる。**最終的な個数はTak確認事項(§8 J1)**。

## 5. デザイン方針

### 配置場所(推奨)
新規サブディレクトリ `labs/ui-fundamentals/knowledge/` を作成:
- `knowledge/index.html`(ポータル)
- `knowledge/spacing.html`(余白記事)
- `knowledge/assets/`(自作図解SVG等)
- `knowledge/tokens.css`(**転写トークン**を単一ソース化)

`prototype/` には触れない。

### トンマナ(推奨: 独立させる)
プロトタイプ(トレーニングUI)と知識ポータル(読み物)は用途が違うため**トンマナは独立**させる。ただし設計原則(出典チップ・事実/解釈分離・誠実さ)は共有。トレードオフ: 独立させると一貫性の管理コストは上がるが、読み物として最適化できる。BONO本体との整合時期はTak確認事項(§8 J4)。

### シンプル洗練 + グラデーション/シェーダーの品ある使い方(節度を"指標化"する)
「余白の記事の見た目が、余白設計の模範であること」(自己言及的品質)を最優先。アクセント表現は以下の**節度ルール**を守り、§6で機械/目視チェックする:
- グラデーション/シェーダーは **ヒーロー領域・セクション区切り・図解のアクセントに限定**。本文テキストの背後には敷かない(可読性優先)。
- アクセント適用領域が全画面面積の一定割合(目安: 15%以下)を超えない。
- `prefers-reduced-motion` で動きを止めるフォールバック必須。
- グラデーション上にテキストを載せる場合もコントラスト比(F-01)を満たす(未丸めで計算)。
- 技術は **CSS/軽量Canvasシェーダーを既定**、WebGLの重い実装は要相談(§8 J2)。

### 自己言及的品質のための「値の転写」(README原則の適用)
台帳README「数値を発明した瞬間にクオリティは落ちる」に従い、**ページ自身の全余白を宣言済みトークンから転写**する。推奨: **8px基本グリッド + Q-06のスケールを転写**した `tokens.css`(例: `--space-2:8px; --space-3:16px; --space-4:24px; …`)を単一ソースにし、すべての margin/padding をこの変数だけで指定。生の px を直書きしない。これにより §6 の決定論チェックが機械化できる。

### フォント/画像
- フォント: UberMoveは非公開(Q-01)。**Noto Sans JP / system-ui スタック**を使用。
- 図解: **経路①(自作図解)が既定**。HIG/M3/Androidの図版はライセンス未確認で使用禁止(README画像ポリシー)。GOV.UKのみOGL v3.0でライブHTML iframe埋め込み可(F-12が取れた場合の実例に活用)。実物スクショを使う場合は引用5条件を満たす。

## 6. 評価指標(最重要ゴール)

「実装→評価→改善点抽出→再リサーチ→再実装」のループを回す軸。**機械チェックはスクリプト化して繰り返し実行**(スクリプトは `knowledge/checks/` に置く)。各指標に「誰が/どうやって/合格基準」を定義。ループ停止条件 = **機械チェック全項目100% かつ 人間評価が全閾値クリア**。

### A. 知識の正確性(機械チェック)
| 指標 | 誰が/どうやって | 合格基準 |
|---|---|---|
| A-1 出典カバー率 | スクリプト(`check-citations.js`)が記事HTMLをパースし、規範・数値主張の数と出典チップ(台帳ID+URL)付き主張の数を数える | 出典付き主張数 ÷ 規範・数値主張総数 = **100%** |
| A-2 事実/解釈の分離率 | スクリプトが `data-type="fact"|"interpretation"` 属性を数え、解釈文が全てラベルを持つか検査 | 解釈文のラベル付与率 = **100%**(未ラベルの解釈文0件) |
| A-3 反例の存在 | スクリプトが「反例」マーカー(`data-role="counterexample"`)の有無を確認 | 記事内に**1件以上**(項目9のBase 2px刻み) |
| A-4 出典の実在性 | 各出典URLが台帳の該当エントリに実在するか突合(台帳mdをパース) | 記事の全出典IDが台帳に存在 = **100%** |

### B. 初心者の理解・解像度向上(人間評価)
| 指標 | 誰が/どうやって | 合格基準 |
|---|---|---|
| B-1 Before/After批評テスト | 初心者2〜3名(オズテストの座組を流用 `docs/02-research/`)。同一の実物スクショを**読前・読後**に批評させ、余白に関する具体的指摘の数と語彙を比較 | 読後に**具体的指摘が平均2個以上増加**し、記事語彙(8pxグリッド/近接/タッチターゲット等)を最低2語使う |
| B-2 理解度ミニテスト | 記事末に4〜5問(例: 「グループ内とグループ間、余白が広いのはどっち?」)。実施は読者本人 | 正答率 **80%以上** |
| B-3 用語の自己説明 | 読者に主要3語を自分の言葉で説明させる | 3語中2語を誤りなく説明できる |

### C. 読み体験(代理指標)
| 指標 | 誰が/どうやって | 合格基準 |
|---|---|---|
| C-1 読了時間 | 文字数を計測(スクリプト)。日本語読速 約400〜600字/分を前提(この前提を記事にも明記) | 本文 **4,000〜6,000字**(=約10分。プロトタイプの「10分で読める」規約に整合) |
| C-2 スクロール到達率 | localStorage にスクロール深度をログ(プロトタイプの進捗保存手法を流用)。テスト参加者で計測 | 参加者の**過半数が最終セクションまで到達** |
| C-3 図解比率 | スクリプトが項目数と図解数を突合 | **全9項目に最低1つの図解**(図解:項目 ≥ 1:1) |

### D. デザイン品質(自己言及・機械チェック)
| 指標 | 誰が/どうやって | 合格基準 |
|---|---|---|
| D-1 余白のグリッド適合(自己言及) | Puppeteerで `getComputedStyle` を全要素に対し実行(`check-spacing.js`)。全 margin/padding が宣言トークン集合(§5)の値に一致するか検査 | トークン外の余白値 **0件**(=ページ自身が模範) |
| D-2 コントラスト | スクリプトが前景/背景色からコントラスト比を**未丸め**で計算(F-01準拠) | 本文4.5:1・大テキスト3:1を**全テキストで達成**。グラデーション上テキストも合格(最明・最暗の両停止点で検査) |
| D-3 本文行間 | line-height を検査(F-11の値1.5を「安全な初期値」として自サイトに採用。F-11自体は堅牢性基準である点に注意) | 本文 line-height **≥ 1.5** |
| D-4 アクセント節度 | アクセント(グラデ/シェーダー)適用領域の面積比を計測 or 目視+チェックリスト | 適用面積 **≤15%**、本文背後への適用**0件**、`prefers-reduced-motion` フォールバック**あり** |
| D-5 タップ領域(記事内リンク/ボタン) | スクリプトで外接矩形を計測(F-04) | 押せる要素すべて **24×24px以上**(間隔例外考慮) |

### E. 事業ゴール適合(「ここで学べば世界で戦える」)
| 指標 | 誰が/どうやって | 合格基準 |
|---|---|---|
| E-1 一次ソース比率 | スクリプトが出典を一次(HIG/M3/GOV.UK/WCAG/NN/g/Base)と二次に分類 | 出典の **90%以上が一次ソース** |
| E-2 独自性(反例・方針比較) | 目視レビュー(Tak or 評価者)。「よくある8px解説記事」との差分=反例/実DS実値/事実解釈分離があるか | チェックリスト**全項目Yes**(反例あり/実DS実値あり/事実解釈分離あり) |
| E-3 信頼感の主観評価 | テスト参加者に「この記事を書いた場所で学び続けたいか」5段階 | 平均 **4.0以上** |

## 7. 実装フェーズ分割(縦切り順・各完了条件つき)

| Phase | 内容 | 完了条件 |
|---|---|---|
| **P1 台帳補強** | §2-2 の R1・R2・R4 を取得し F-11 / F-12 / S-16(と取得できれば S-15)を台帳に新設。取得失敗は「未取得」明記 | 新エントリが一次ソース原文引用付きで台帳に存在。記事で使う全知識に台帳IDが割り当たる |
| **P2 記事構成の確定** | §3 の9項目を、各項目「主張文・出典ID・図解仕様」まで確定した構成表にする(本文はまだ書かない) | 全9項目が出典ID紐付け済み。反例(項目9)の素材(Q-06)確定 |
| **P3 骨格+トークン+チェック基盤** | `knowledge/` 作成。`tokens.css`(転写値)、`index.html`(ポータル骨格+プレースホルダ)、`spacing.html` の空骨格、`checks/`(A・C・D系スクリプト) | ポータルが表示され、チェックスクリプトが空ページに対し実行できる |

**チェックスクリプトの実行系(2026-08-30決定)**: 第一段は**ゼロインストールの静的スキャン**(Node標準のみ、npm install不要)とする — (a) HTML/CSSソースを正規表現+パースで走査し、`tokens.css`以外での margin/padding/gap への生px/rem直書きを検出=D-1、(b) トークンの色値からコントラスト比を直接計算=D-2(グラデーションは全停止点で計算)、(c) line-height検査=D-3、(d) 出典チップ/data-type属性のカウント=A系、(e) 文字数・図解数=C系。Puppeteerによる`getComputedStyle`実測(D-1/D-5の厳密版)は後続ループでの**アップグレードオプション**とし、初回は必須にしない。
| **P4 記事実装** | `spacing.html` 本文+自作図解(経路①)+アクセント(節度ルール順守)を実装 | 記事が全項目・全図解・出典チップ付きで完成 |
| **P5 評価ループ** | 機械チェック(A/C/D/E-1)を回し→改善点抽出→(必要なら)再リサーチ(P1へ戻る)→再実装。人間評価(B/C-2/E-2/E-3)を実施 | **停止条件: 機械チェック全100% かつ 人間評価が§6の全閾値クリア** |

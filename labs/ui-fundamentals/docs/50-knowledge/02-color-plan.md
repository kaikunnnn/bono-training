## 1. ターゲット読者と体験ゴール

### 読者ペルソナ（1本目と同一）
- BONO会員の初心者。「色はセンスで選ぶもの」「目立たせたいから鮮やかにする」と思っている。コントラスト比という言葉は聞いたことがある程度で、数値で語れない。
- 1本目「余白」を読んだ直後の読者を想定（ポータルの次カード導線から流入）。

### 体験ゴール（読前→読後）
| 観点 | 読前(Before) | 読後(After) |
|---|---|---|
| 語彙 | 「なんかダサい色」「見づらい」 | コントラスト比4.5:1／非テキスト3:1／セマンティックカラー／グレースケール階層／トーナルパレット を使い分けて言える |
| 判断 | 色を単体の好みで選ぶ | 「本文は背景と4.5:1」「有彩色はアクセント1色に絞る」「色だけで状態を伝えない」等、根拠のある初期値を持てる |
| 批評眼 | 良し悪しを言語化できない | 実物を見て「この薄いグレー枠は3:1未満」「エラーが赤だけでアイコンが無い」と具体で指摘できる |
| メタ認識 | 「鮮やかで目立つ色＝良い」「正解の配色がある」 | 「Base は黒基調、GOV.UK は青基調＝文脈で正解が変わる」「純黒も #000 と #0b0c0c で割れる」と理解する（断定禁止の体現） |

**体験の核**: 読後に「世の中のUIの色が"読める/読めない"で見える目」になる。1本目の「余白が見える目」とモチーフを揃え、2本続けて読んだ読者に一貫した成長実感を与える。

## 3. 記事の構成案 — 「UIの配色で知るべきX個」

### X の決定 = **9個**

**決定根拠**:
1. **既存＋追加カバレッジで9個の独立した色概念を過不足なく覆える**（役割／テキストコントラスト／非テキストコントラスト／色だけに頼らない／グレースケール階層／アクセント節度／意味色／パレットの作り方／反例）。各項目に台帳IDが1つ以上紐づく（下表）。
2. **C-1（本文4,000〜6,000字）に収まる**: 1本目は9項目で5,042字。同粒度（1項目≈500字）で約4,500〜5,000字と見積もれ、範囲内。
3. **Takの2本比較という本タスクの目的**: 1本目と同じ9項目・同じ物語の弧（機能→中核の物差し→関係→実値→プラットフォーム差→体系→反例）にすると、余白と配色を横に並べたとき構造が一致し、比較・改善判断がしやすい。

**代替案の検討**:
- **8個案**: F-02（AAA）を項目2（テキストコントラスト）に統合し、独立項目を1つ減らす。→ 却下。トーナルパレット（項目8）を落とすと差別化（E-2）が弱まり、8だと1本目との構造対応も崩れる。ただし**実装後に字数が6,000字を超える／薄い項目が出た場合の縮約先はF-02の統合**とする（フォールバック）。
- **10個案**: 項目8をロール（S-17）とトーナル生成（S-18）の2項目に分割。→ 却下。S-18は取得未確定でリスクが高く、10項目だと字数超過・ミラーの法則7±2の上限も超える。

各項目に「出典（台帳ID）」「図解の種類（すべて経路①=自作図解が既定）」を明示。**新規IDは P1 取得後に確定**（下表の (新) は取得待ち）。

### P2 主張文ドラフト表（9項目・事実/解釈の分離）

**implementer はこの文を再導出せず、本文の核として肉付けすること。事実文は必ず該当台帳エントリの原文引用のパラフレーズであること。(新)ID の事実文は P1 取得後に原文照合して確定する（下記は取得済み情報に基づくドラフト）。**

| # | 事実（data-type="fact"） | 解釈（data-type="interpretation"） |
|---|---|---|
| 1 | Material 3 は色を「ロール（役割）」として定義し、UIの各要素に用途で色を割り当てる（S-17）。実務の観察でも、洗練された画面は色が個別に選ばれず「コントラスト基準と視覚的重みが揃うよう体系的に生成されている」（観察: 洗練-05／A-03 Stripe）。Uber Base も色をトークンで一元管理する（Q-04） | だから色は「飾り」ではなく「役割を運ぶ道具」。まず「この色は何の役割か（本文か・アクセントか・状態か）」を言えるようにするのが第一歩。1色ずつ好みで選ぶのをやめる |

## 5. デザイン方針（1本目を厳守・配色記事固有の追加規約）

### テンプレート・トークンの継承
- `color.html` は `knowledge/spacing.html` の**構造・CSS・クラス命名・Canvasシェーダー実装・reduced-motionフォールバックをそのまま流用**する。差し替えるのは本文・図解・出典チップ・目次・タイトルのみ。
- `knowledge/tokens.css` を単一ソースとして共有。ページの chrome（余白・行間・chrome色）は既存トークンのみで指定。**生px/hexの直書き禁止**（D-1・新hexチェックの前提）。

### 配色記事に固有の「specimen（見本）トークン」規約 ★最重要
配色記事は「実在DSの実hex」を見本として見せることが教材の核。これと「生hex直書き禁止」を両立させるため、**見本色もすべて tokens.css に台帳IDコメント付きで転写し、図解からは `var(--…)` で参照する**（=見本色も"転写"になり、自己言及的品質の最強の実演になる）。以下4規約を厳守:

- **(a) specimen トークンを tokens.css に追加**（chrome トークンとは接頭辞 `--swatch-` で分離、台帳IDコメント必須）。例:
  `--swatch-base-ink: #000000; /* Q-04 contentPrimary */`
  `--swatch-base-content2: #4B4B4B; /* Q-04 */` `--swatch-base-content3: #5E5E5E; /* Q-04 */`
  `--swatch-base-disabled: #A6A6A6; /* Q-04・4.5:1未満/無効例外 */`
  `--swatch-base-accent: #276EF1; /* Q-05 */` `--swatch-base-error: #DE1135; /* Q-05 */`
  `--swatch-base-positive: #0E8345; /* Q-05 */` `--swatch-base-warning: #9F6402; /* Q-05 */`
  `--swatch-govuk-ink: #0b0c0c; /* F-15 */` `--swatch-govuk-link: #1a65a6; /* F-15 */` 等。
  すべて P1 取得後の台帳原文と一致させる（発明禁止）。
- **(b) D-2 コントラスト検査の対象は"ページ自身が読ませる本文/UIテキスト"のペアのみ**。specimen トークンは検査ペアに含めない（見本は他社の値であり、意図的に低コントラストの"悪い例"を含むため）。
- **(c) 意図的に不合格な見本**（項目3の薄枠、項目5の #A6A6A6、項目2の低コントラスト例）は、図解内に「悪い例／例外」と明示ラベルを付け、D-2 検査から除外する。数値は正しく示すが「これは満たしていない」と説明する。
- **(d) ページ自身のアイデンティティ色は既存の自前トークン（--color-accent）を維持**。Base の #276EF1 等は「出典付きの見本」としてのみ登場させ、ページの基調色に採用しない。

### 図解・フォント・アクセント節度
- 図解は経路①（自作SVG）が既定。HIG/M3/Android の図版は使用禁止。GOV.UK のみ OGL v3.0 で転載可（§8 J4: 今回は自作SVG見本で代替し、iframe埋め込みは見送り）。
- フォント: Noto Sans JP / system-ui（tokens.css 既定）。
- アクセント節度（D-4）・シェーダー方針は 00-plan.md §5 と同一（ヒーロー＋セクション区切りのみ、本文背後に敷かない、reduced-motionフォールバック）。

## 9. 追補（2026-08-31・Tak要望）: 記事末の理解度クイズ

> Tak: 「記事の最後に少しトレーニングっぽい内容をつけて欲しい。項目のクイズかな。設問があって、選択肢があって選択すると答えと詳細の解説が出るみたいなやつ。簡単な仕組みでいい、あくまで記事だから」

01-eval-log.md の次ループ候補③「記事末の理解度ミニテスト（B-2用の4〜5問）」がTak要望で確定した形。**実装は配色記事（color.html）に入れる。spacing.html への同型クイズ追加はループ2候補**（今回のスコープ外、評価ログに記載）。

### 仕様
- **位置**: まとめの直後・「次に読む」導線の前。セクション見出し例:「理解度チェック — 5問」
- **問数**: 5問（B-2基準の4〜5問の上限）。記事の9項目から出題バランスを取る（例: 項目2コントラスト比の数値／項目4色だけに頼らない／項目5無効グレーの例外／項目6アクセント節度／項目9反例=唯一の正解はない）
- **形式**: 1問 = 設問文＋選択肢3〜4個（ボタン）。選択すると:
  - 選んだ選択肢に正解○/不正解×の表示
  - 正解の選択肢をハイライト
  - **解説パネルが開く**: 正解の理由＋関連する記事内項目へのアンカーリンク＋出典チップ（台帳ID）。誤答選択肢の「なぜ違うか」も1行ずつ
- **仕組み（簡単に・あくまで記事）**:
  - 依存ゼロの**素のHTML＋最小限のvanilla JS**（数十行）。`<button>` ベースでキーボード操作可、`aria-expanded`/`aria-live` など最低限のアクセシビリティ
  - 採点・保存・送信は**しない**。選び直しは自由（もう一度押せる）
  - JS無効時のフォールバック: `<noscript>` で「解説は各項目セクションを参照」と表示（または details/summary 併用でも可、実装者判断）
  - スタイルは tokens.css の既存トークンのみ（正解=--color-fact系、不正解=--color-interp系 など既存の意味色を流用。新色を発明しない）
- **文体規約の適用**: 設問・解説も断定禁止ルールに従う。解説の知識主張には出典（台帳ID）を付ける＝クイズもA-1出典カバー率の対象
- **機械チェック**: check-content（または新設 check-quiz）に「問数=5」「各問に解説あり」「解説に台帳ID出典あり」「正解フラグが各問ちょうど1つ」の検査を追加

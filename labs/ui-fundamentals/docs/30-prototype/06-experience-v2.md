# 体験v2 — Takフィードバック(2026-07-07)の整理と新方針

## 1. フィードバックの整理(5点)と原因分析

| # | フィードバック | 根本原因 |
|---|---|---|
| F1 | **問いが唐突**。初心者は「ユーザーが思うべきことは?」に答えられない。答えさせるのではなく「基本」を共有すべき | 「問う→考えさせる→型」を全ステップに適用した設計ミス。**作る前に必要なのは問答ではなくインプット**。問いに意味が出るのは「作った後」(比較・言語化) |
| F2 | **実物を触らせないとダメ**。スクショ提示では探求が上がらない。デザインの基本は世の中のものを見て・触って・自分で学ぶこと | 実物を「見せる資料」として扱った。**実物は触りに行かせる対象**(フィールドワーク)。探求は問答ではなく実物接触から生まれる |
| F3 | **断定がミスリード**(「UberもAirbnbもパスワードを作らせない…今日一番大事な判断」)。そうじゃないサービスもある | 観察事実(4サービス)を一般法則のように語った。**サービスごとに方針が違うことこそが学び**。反例と「なぜ各社そうするか」の方針を並べるべき |
| F4 | **制作までが長い**(7ステップの問答ゲート)。インプントは自由に読ませ、いつでも見返せるように | ゲート式の直列ステップが自由を奪い、テンポを壊す。インプットは**参照物**(スクロールで読む・制作中も見返せる)であるべき |
| F5 | **「作ること」が最初に伝わらない**。作りながら学ぶ期待とズレる | 学習が主役・制作が従の画面構成。**制作がセンター**で、学習は制作の伴走であるべき |

## 2. 新方針(標準形v2: 「制作センター型」)

> **旧**: ブリーフ → 問答ゲート7ステップ → 制作 → 比較 → 言語化
> **新**: ブリーフ(今日作るものを最初に宣言)→ **インプット(答えさせない・3カード・自由閲覧)** → **制作(センター・インプット常駐)** → 比較 → 言語化(問いはここに集約)

### 原則(フィードバック対応)

1. **教える、聞かない(F1)**: インプットは「基本の共有」。クイズ・回答ゲートを全廃。問い(同じ判断/違う判断/学びの1文)は**作った後**の比較・言語化に集約する——作った後なら初心者でも答えられる
2. **実物は触りに行かせる(F2)**: インプットに**フィールドワーク**を組み込む。「実際にAirbnbとSpotifyの登録画面を自分のスマホで開いてみよう(登録完了は不要)+観る観点3つ」。スクショは触れない人のフォールバックに格下げ
3. **断定禁止・方針比較(F3)**: 「必ずこう」をやめ、**サービス別方針表**で提示する——「Uberはこう(方針: 電話が主ID)、GOV.UKは今もパスワード式を定義(方針: 行政の本人性)。あなたのTempoは?」。反例を必ず1つ以上載せ、事実(観察)と解釈(方針の推測)を表示上も分離する
4. **インプットは参照物(F4)**: ゲートなしの1ページ・3カード構成。制作画面に「インプットを見返す」を常駐させ、いつでも戻れる
5. **制作ファースト(F5)**: ブリーフの1行目が「今日はこの画面を作ります」。インプットの冒頭にも「読み終えたら作ります(目安10分で読める)」と制作までの距離を明示

### インプット3カードの型(お題タイプ共通)

| カード | 中身 | 由来 |
|---|---|---|
| ① この画面の基本 | 画面タイプの用事・定番の構成(教える口調で) | 旧STEP0-1の内容を問答から解説へ変換 |
| ② 実物を触る | フィールドワーク(実URL+観る観点)+サービス別方針表(事実/解釈を分離)+観察メモ欄(**任意**) | F2/F3の中核。壁の中のお題は観察記録で代替 |
| ③ 部品の基本 | パターン辞典(定義=DS引用/挙動/使用サービス)を参照形式で | 旧パターン辞典の昇格(折りたたみ→カード) |

## 3.5 ブリーフ設計原則(2026-07-07追加・Tak承認)

**「情報(何を載せるか)は与える。構造(どう組むか)は与えない。」**

- 根拠: 実務では要件(載せる情報)は与えられ、構造化がデザイナーの仕事の核 / 初心者は要件と構造を同時に決められない(H1)/ Frontend Mentorはキットで要件まで与える(D-01)、一文だけのSharpen/DailyUI型は挫折構造(D-06)/ 情報が共通だと比較(判断の比較)が成立する
- ブリーフの構成を「①シナリオ ②**画面に載せるもの(情報=要素リスト)** ③完成条件(=品質の物差し) ④部品 ⑤提出」に分離。**②と③を混同させない**(チェックリストから要素を逆算させない — 2026-07-07フィードバック)
- 情報の与え方は習熟で3段階に外す: **序盤=確定リスト**(構造だけ自分で)→ **中盤=多めの候補リストから削らせる**(取捨選択も判断に)→ **卒業制作=シナリオのみ**(要素定義から自力)

### スタイルキットの原則(2026-07-08追加・Takフィードバック起点)

**「スタイル(色・文字・寸法)と部品の見本も、キットの一部として与える。」** 学習者に渡すブリーフは「①シナリオ ②載せるもの ③できたかチェック ④**部品とスタイル(トークン+ライブ見本+使い方1行、全てQ台帳から出典付き)** ⑤提出」の5点構成。

- 根拠: FMのstyle-guide.md同梱(D-01/原則-01)/「判断済みの部品が初心者の摩擦を下げる」(原則-07: Refactoring UI)/ Q台帳のトークンを模範だけでなく**学習者にも渡す**(渡っていなかったのは4層リファレンスの配布漏れ)
- 位置づけの言葉: 「今日はスタイルで迷わなくてOK。プロも部品セット(デザインシステム)から作りはじめる——それも練習のうち」
- スタイルも足場: 序盤=完全指定 → 中盤=一部を選ばせる(例: ブランド色の選定) → 上級=トークン設計自体をお題に
- 経緯の記録: 当初のプロトタイプはスタイル層を学習者向けキットから落としていた。**ユーザーゴール(迷わず作って判断を学ぶ)から正当化できない欠落**と判断し、パターン2で修正(prototype/pattern2.html の kitHtml)

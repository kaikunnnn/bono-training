# お題サービス 体験設計書(工程A成果物)

- 2026-07-06。根拠: 実在サービス調査3本(E=学習体験 / G=AIガイダンスUI / D=デザイン練習)+既存台帳
- 原則: **すべての設計判断に観察IDを付ける**。付けられない判断は「仮説」と明記

---

## 1. 体験の背骨 — 学習ループの再定義

1お題=1セッションの学習ループを、調査に基づき5局面で確定する:

> **①ブリーフ(キット)を受け取る → ②パターンをマイクロステップで学ぶ → ③作る(Figma並走)→ ④比べる(観点別)→ ⑤言語化して完了**

DailyUI本家は①のみでフィードバック機構が存在しないことを事実確認済み(E-10)。②と④がこのサービスの存在理由。

## 2. 設計判断(A-1〜A-8、すべて根拠付き)

### A-1. 対話の器: チャット型ではなく「レッスン型ステップUI」+オンデマンド対話

- **判断**: 主画面はチャットのタイムラインではなく、**1画面=1マイクロステップ**が置き換わるレッスン型。AIへの自由質問・「もっと詳しく」は各ステップに常駐する補助動線として付ける
- **根拠**: 学習サービスはすべてステップ/レッスン単位(E-04/E-05: Brilliantは「2〜4文の説明+即・問い」のシーケンス、E-06: freeCodeCampは1指示1実装)。ガイドAIの発話は「1メッセージ=1要点+次のアクション」が共通文法で、長い説明は要求時に退避(引用-04: Khanmigo/Grammarly/Duolingo Max)。純チャット型で技能練習を成立させている前例は今回の調査で確認できなかった
- **効果**: 「ただのChatGPTに見える」問題(プロトタイプ計画のリスク3)もこれで構造的に回避

### A-2. 引用の表示: 折りたたみチップ+ステップ末尾まとめ(確定)

- **判断**: 主張ごとに軽い出典チップを常時表示。タップで「出典名+該当箇所の原文引用+『デザインシステムで見る→』(新タブ)」を展開。ステップ末尾に出典一覧を再掲
- **根拠**: 確認した全プロダクト(Perplexity/ChatGPT/Claude/Grammarly)が「軽いマーカー常時+詳細はオンデマンド」の二層(引用-01)。全文インライン常時表示の前例はゼロ(引用-01)。主張↔出典は1対1対応・実在リストからのみ引用(引用-02 — Perplexityの"Never generate your own URLs"は我々の嘘なし設計と同型)
- 当初の「3案切替で比較」は不要になった(実物調査で決着)。v0にデバッグ用切替を残すのは任意

### A-3. ブリーフは「一文のお題」ではなく「4点キット」

- **判断**: お題は ①シナリオ(誰の・何のための画面か)②完成条件チェックリスト ③使ってよい部品(経典DSの該当トークン/パターン引用)④提出テンプレート(判断理由の記入欄)の4点セットで渡す
- **根拠**: 継続を作っているFrontend MentorはZIP一式(お題文+状態別完成画像+style-guide.md+提出テンプレ)で渡す(D-01/原則-01)。一文プロンプト型(Sharpen/DailyUI)は「その先が全部自力」で終わることを確認(D-06/E-10)。「判断済みの部品を渡す」こと自体が価値(原則-07 — Refactoring UI/Mobbin)

### A-4. 合格条件の先出し(①と④を同じ物差しでつなぐ)

- **判断**: ブリーフ画面で「このお題で満たすべきチェックリスト」を最初に見せ、④の比較・フィードバックは**同じチェックリスト**への達成/未達で返す
- **根拠**: freeCodeCamp Labsは空エディタ+テストスイート先出し(E-06)、Frontend Mentorはブリーフ要件への行レベル評価(E-08)。体験-03として帰納済み。我々の決定論チェックリスト(付録A)がそのままこの物差しになる

### A-5. ②のマイクロステップ粒度: 「説明2〜4文+実例+小さな問い」

- **判断**: パターン教育の1ステップ=「パターンの説明2〜4文+実在DSからの引用(チップ)+『あなたのお題ではどうする?』の小さな問い」。読んで進むのではなく**答えて進む**
- **根拠**: Brilliantの実測粒度(E-05)、Duolingoの「学習者中心のインタラクティブ」原則(E-02)、体験-01として帰納済み。既存台本の「問う→考えさせる→型」と一致し、実在サービスの裏づけが取れた

### A-6. ③のヒントは3段階・任意(答えでなく推論を渡す)

- **判断**: 制作中のヒントは「1段目: 着眼点の問い → 2段目: 見るべきDS該当箇所 → 3段目: 模範の部分開示」。強制表示しない
- **根拠**: Brilliantの誤答時scaffolding(E-05)、Duolingoのoptional hints+Explain My Answer(E-03)、体験-02。ガイダンスの実在形は「読む順番・作る順番の指定」という軽量形式(D-02/原則-02)——手取り足取りの対話ヒントを常時出すサービスは確認できなかった

### A-7. ④の比較: 「重ねて比べて、直して、また比べる」+観点別before/after

- **判断**: 比較は(a)自分/模範/実物の3点並置(b)**観点別カード**(余白・階層・色・状態…)に分解した差分提示(c)「直して再比較」ボタンで反復ループ、の3点構成
- **根拠**: Frontend Mentorの比較スライダー+再スクリーンショット反復(E-09)、比較体験が課金の中心になるほど価値が重い(D-03/原則-03)、before/after形式が最小教材単位(D-09/原則-08)。既存のSTEP4三点比較設計に、観点別分解と反復ループを追加する

### A-8. ⑤の完了: 判断の言語化を提出フォーマットで強制+蓄積

- **判断**: 完了時に「私は◯◯のとき、◯◯という理由で◯◯する」の言語化を必須欄にする。完了作品+言語化は自動でポートフォリオページに蓄積
- **根拠**: Uxcelは「決定の理由を説明せよ、丁寧なほど良いフィードバックが返る」と提出側で言語化を強制(D-05/原則-04)。提出物が自動でMy Projects=ポートフォリオになる(D-05/原則-05)。BONO思想「なぜこのデザインかを語れる」と実在サービスの設計が一致

## 3. 画面フロー(6画面)

```
[1] お題一覧 ──→ [2] ブリーフ(キット) ──→ [3] 学習ステップ ──→ [4] 制作(Figma並走)
                                                                      │
[6] 完了・ポートフォリオ ←── [5] 比較・フィードバック ←──────────────┘
                                     └──「直して再比較」→ [4] へ戻るループ
```

| # | 画面 | 主要要素 | 根拠 |
|---|---|---|---|
| 1 | お題一覧 | お題カード(難易度タグ・学べるパターンのタグ・所要時間)、進行中リスト | D-02(難易度絞込・着手の可視化)、原則-05 |
| 2 | ブリーフ | シナリオ / 完成条件チェックリスト(先出し) / 使ってよい部品(DS引用) / 「はじめる」 | A-3, A-4 |
| 3 | 学習ステップ | マイクロステップカード(説明2〜4文+引用チップ+小さな問い+回答欄)、進捗ドット、「もっと詳しく」 | A-1, A-2, A-5 |
| 4 | 制作 | コンパクト表示(チェックリスト常駐+3段ヒント+経過時間)。Figmaは学習者自身の環境で並走 | A-6, 体験-03 |
| 5 | 比較 | 3点並置(自分/模範/実物)、観点別before/afterカード、チェックリスト判定、再比較ボタン | A-7 |
| 6 | 完了 | 学びの言語化(必須欄)、獲得パターンの記録、ポートフォリオ蓄積、次のお題推薦 | A-8, E-04(詰まり追跡→次の推薦) |

## 4. このプロトタイプ(I1目的)での実装スコープ

- 目的=「AIがDSを参照して作ったステップ設計・お題設計が、Webページとしてどう見えるか」をTakが判断する
- **作る**: 画面2〜6の1本の通し(お題01)。コンテンツはgolden sample+台帳から。画面1は簡易(カード数枚のダミー)
- **作らない**: ログイン/保存/ストリーク/課金/ライブAI採点(I6縮小の決定どおり)。比較のスクリーンショット自動生成は手動アップロードで代替
- 判断の言語化欄・チェックリスト判定・引用チップは**必ず入れる**(このサービスの固有価値の可視化がプロトタイプの目的だから)

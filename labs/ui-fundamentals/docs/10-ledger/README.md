# リファレンス台帳の方法論 — 4層構造

2026-07-04 改訂(同日中に3層→4層へ再改訂)。当初の台帳は「正しさ」の根拠に偏っており、「洗練」の根拠が欠けていた。
さらに3層版にも欠落があった: トークンと記事だけでは**実在の画面の「型」**を再現できず、模範が「どこにも存在しないUI」になる。
**答えの信頼とは「これは実在するUIである」と実物を提示できること。** これを最上位のリファレンスに置く。

## 4層の定義(上ほどground truthに近い)

| 層 | ファイル | 出典の種類 | 役割 | アウトプット先 |
|---|---|---|---|---|
| **⓪ 実物画面層**(V-実測) | quality-visual-analysis.md(V-06以降)+ screenshots/ | 実在アプリの**スクリーンショット実物** | **ground truth**。模範が再現すべき「型(アーキタイプ)」 | 模範の画面構成そのもの。STEP4で「模範 vs 学習者 vs 実物」の3点比較に使う |
| **① ルール層**(F/P/S) | foundations.md / patterns-forms.md / principles-structure.md | 規範文書・ガイドライン(WCAG, HIG, Material, GOV.UK, NN/g) | **間違いを防ぐ**。正しさの下限を保証 | STEP0〜2のAI発話の根拠 / STEP3の決定論チェックリスト |
| **② クオリティ層**(Q) | quality-base-uber.md | 実在DSの**公開トークン(実コード)**(Base Web等) | **洗練の実値**。模範の見た目の水準を決める | 模範UIの数値(色hex・サイズ・角丸・行送り)はここから**転写**する。値を発明しない |
| **③ ビジュアル実例層**(V/洗練) | quality-visual-analysis.md | 実画面のHTML観察+各社公式デザイン記事 | **構造・コピー・トーンの帰納** | 模範の画面構成・見出し文言・要素数・余白の思想 |

## ⓪実物画面層の取得パイプライン(信頼度順)

1. **ブラウザ実測**: Claude in Chrome(拡張)で実サービスの登録/ログイン画面を実際に開き、スクリーンショットを取得日付きで保存。一次ソース・再現可能・最も強い
2. **Mobbin**(mobbin.com): 実アプリ画面の業界標準ライブラリ。お題ごとに「同じ画面タイプの実物5枚」をキュレーションする用途に最適(要アカウント。ブラウザ実測と併用)
3. **ユーザー/運営者提供のスクリーンショット**: 出所と日付を記録して採用
4. App Storeプレビュー画像・公式プレスキット(ログイン画面はまず含まれない点に注意)

運用ルール: お題1つにつき**実物3〜5枚**を先に集めてから模範を作る。模範完成後、実物と**サイドバイサイドで照合**し、乖離があれば模範を直す(逆ではない)。

## 題材選定ポリシー(2026-07-04決定)

**お題の選定基準は3条件**: ①実物画面が5枚集まる ②経典にできる公開DSがある ③テイスト依存が低い(フォーム/設定/リスト/データ表示系)。「有名かどうか」自体は基準にしない。

その上で、リファレンスの構成は**「SVデフォルト+日本対比」**とする:

- **主リファレンス(デフォルト)**: シリコンバレー級サービスの実物+公開DS。3条件を最も満たしやすく、ユーザーのメンタルモデル(S-11 ヤコブの法則)の形成源でもあるため、型と品質の基準器に使う
- **対比リファレンス(各お題に1枚)**: 同じ画面タイプの**日本のサービス実物**を必ず添える。「なぜAirbnbとLINEで違うか=文脈が違えば正解が変わる」をSTEP4の問いにする

この構成の意図(縛りにしない理由): SV一色に縛ると ①同質化バイアス(良いUI=SV風という誤学習。受講生の実務は日本のUI)②日本語UI特有の設計(姓名順・住所・全角半角・和文行送り)の欠落 ③「有名=正しい」の権威バイアス(批判的比較という教材思想と矛盾)が生じるため。

注意: 実物スクリーンショットの教材利用は批評・比較研究としての引用の範囲に収める(出典明記・必要最小限・必ず論評を伴う)。他社の実測値は「観察された事実」として引用し、ブランド要素(色・ロゴ)は自前トークンに置き換える。

## 画像・実例の利用ポリシー(2026-07-08確定・3経路)

| 経路 | 方式 | 条件・キャプション形式 |
|---|---|---|
| ① 自作図解 | 仕様をもとに自分で作図 | 制約なし。「◯◯の仕様をもとに作図」を付ける |
| ② 実物スクショの引用 | 解説に添えて表示 | 引用5条件(解説が主/必要最小限/出典明記/改変しない/論評を伴う)。形式:「引用: ◯◯(プラットフォーム)の△△画面。YYYY年M月D日時点のスクリーンショット。□□を解説する目的で引用しています。」 |
| ③ 公式コンテンツの転載/埋め込み | ライセンスが許すもののみ | **GOV.UK: OGL v3.0を実確認済み(2026-07-08)→ 転載・iframe埋め込み可(帰属必須)**。形式:「Open Government Licence v3.0 / © Crown copyright のもとで表示」。GOV.UKの実例はライブHTML(/components/◯◯/default/index.html)なのでiframe埋め込みが最適 |

## 模範UIの制作手順(この順番を守る)

1. **DS選定**: お題タイプに合う「品質の引用元DS」を1つ決める(Sign Up/フォーム → Uber Base)。以後、模範はそのサービスの品質を再現する
2. **③で構造を決める**: 実例観察から画面構成・コピーの型を取る(例: 見出しは機能名でなく価値提案、要素数最小、有彩色はCTA周辺のみ)
3. **②で全数値を転写する**: 色・サイズ・余白・角丸・タイポは選定DSのトークンをそのまま使う。**デザイナー(AI含む)が数値を発明した瞬間にクオリティは落ちる**
4. **①でチェックする**: 完成物をルール層(コントラスト・タップ領域・フォームパターン)で検査。②と①が衝突したら記録して教材の論点にする
5. 完成した模範は「全数値に出典がある」状態になる

## v1とv2の教訓(実証済み)

- **v1**(紫・独自の値): ルール層だけを守って作った → 正しいが洗練されない
- **v2**(Base実トークン): 3層すべてを通した → 「正しさ ≠ 洗練」の実証。両者の比較自体がSTEP4の教材になる

## 各層の信頼度と更新ルール

- ②はコード由来なので最も信頼できるが、**Web実装の値**である点に注意(ネイティブ固有値は未取得と明記済み)
- ③の「帰納された解釈」は事実ではないので、AI発話では「観察: V-01〜V-03では〜」と事実側を引用する
- どの層も「未取得」の正直な申告を消さないこと。取得できた時点で差し替える

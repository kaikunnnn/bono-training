## 1. 順序の設計思想(学習実例からの採用判断)

| 論点 | 採用 | 根拠 |
|---|---|---|
| 構造が先か、ビジュアルが先か | **構造が先**(階層・レイアウト・グルーピング→部品→色) | 順序-03: 「判断力を上げる」系(Refactoring UI / CareerFoundry UI専門)は構造優先。我々の目的と同じ側 |
| パターンの登場タイミング | **最初から作らせる**(freeCodeCamp型)。ただし設計判断の負荷は段階的に上げる | 順序-02: 「作る対象としてのパターンは早く、設計判断としてのパターンは中盤」— お題形式はこの両立ができる |
| プロジェクトの挿入 | **毎お題=プロジェクト**(定期挿入型) | 順序-04: 長期・実践型は章ごとに作る。DailyUI形式の本質と一致 |
| 足場の外し方 | 新パターン=インプット厚め / 再出題=薄め(v2で「ステップ数」から「インプット量」に改訂) | 標準形v2(06)+体験-06 |
| **情報の与え方(第2の足場軸)** | 序盤=**確定リスト** → 中盤=**候補から削らせる** → 卒業制作=**シナリオのみ** | ブリーフ設計原則(06 §3.5): 情報は与える・構造は与えない |
| アクセシビリティ | 独立お題にせず、**全お題のチェックリストに常駐**(F-01/F-05) | 順序-06で多数派は後半配置だが、数値系は決定論チェックで最初から混ぜられるのが我々の強み |

## 2. I3: 経典routing(パターン×権威の対応)

**基本構成は「部品定義」+「タスク文脈」の2経典**(I2の発見: タスク軸の体系はGOV.UK patternsが唯一)+補助3種:

| 役割 | 経典 | 使いどころ |
|---|---|---|
| 部品の定義・解剖(モバイル) | **Apple HIG / Material 3** | パターン辞典の「定義・挙動」 |
| タスクとしての使い方 | **GOV.UK patterns**("Ask users for… / Help users to…") | お題のシナリオとステップの問い |
| Web管理画面・高密度データ | **Polaris / Primer** | ダッシュボード系お題の部品定義 |
| 実トークン(数値) | **Base Web**(コード) | 模範の色・サイズ・角丸 |
| 数値ルール | **WCAG / HIG / M3** | 決定論チェックリスト |

### カバレッジ検証(嘘のなさ: 地図がカタログを覆うか)

- 共通コア20パターン中、**19が上記12お題で「新」として登場**(未カバー: ツールチップ/ポップオーバー → お題10か12の部品として吸収 ⚠️)
- 各お題の「再出題」列により、主要パターン(階層/グルーピング/フォーム/言葉)は**最低2回**(足場あり→なし)出現する
- 実物の壁: 外◎が5、外○が2、壁が5 — 壁のお題は「実測観察の記録」方式(お題02で実証済み)で成立

## 4. Tak判断待ちの論点(⚠️)

1. **12お題の粒度と並び** — 特に05(選択コントロール)と11(通知)は統合可能。10お題に圧縮する案もある
2. **日本対比の実装** — 各お題1枚の方針は決定済みだが、対比画像の収集はChrome実測かMobbin待ち。地図上は「候補」止まり
3. **第3幕の難易度表記** — 10〜12は「中級」タグにすべきか
4. **卒業制作(12)の形式** — 通常の7ステップか、ブリーフと物差しだけ渡す「自力モード」(体験-06の最終形)か

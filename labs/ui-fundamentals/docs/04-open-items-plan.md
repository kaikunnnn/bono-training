## ビジョンの再定義(2026-07-06、Takの語りから)

- **学習単位は「お題」ではなく「UIパターン」**。お題はパターンを出力させる乗り物
- DailyUIとの違い: **実務的なお題**(電卓等の非実務題材を排し、ログイン/SNSフィード/投稿フロー/ダッシュボード等、実務で作る画面)。学ぶのは基本UIパターン(フォーム/カード/ナビ/メニュー/ボタン配置…)
- 学習エンジン: **実在DSの定義からパターンをステップで input →(お題で)output**。「このパターンはこういう挙動、こういうサービスで使われる、だから真似して作ろう」を、実ソース引用で
- お題は、経典デザインシステム(HIG/Material/Primer/Base等)のパターン定義から**導出**する

## I1: このビルドの目的(確定 2026-07-06)

**AIだけでデザインシステムを参照し、ステップ設計・お題設計を行い、それをWebページにしたときに『どういう内容と進め方になるか』を、Tak自身が見て判断するプロトタイプ。** ユーザーに見せる前の、リファレンスベースでどこまで使えるものになるかの品質プローブ。

### この目的が決めること(スコープの確定)
- **検証先行の規律は、このビルドには適用しない**。ビルド自体が実験(コンテンツ品質を見るのが目的)。実ユーザー検証(I8)は「見せる前」なので明確に後回し
- **中核で問うのは「リファレンス由来のコンテンツと流れの質」**。よってエンジン(I2〜I5)が主役
- **I6の実行時AI(学習者のFigma作品を live で採点)はスコープ外**。このプロトタイプは「内容と進め方」を見せるもので、live採点は不要。ただし「評価の中身=リファレンス由来のルーブリック」はコンテンツとして表現する
- **I7(定着・動機)・I9(スケール)・I10(法務)は後回し**(時期を明記して保留)

## I6で見えた設計の急所(記録)

**入力ステップでパターンを教える「DSの定義」が、そのまま出力を評価するルーブリックになる。** 入力と評価が同じ実ソースを共有する=評価基準を発明しない=「嘘のなさ」が評価の公正さに直結。live採点を実装する段(製品化)でも、この一点が中核。

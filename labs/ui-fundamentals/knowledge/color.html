UIの配色で
知るべき9個

色は「センスで選ぶもの」ではありません。コントラスト比という物差しから、色だけに頼らない設計・無彩色の階層・アクセントの節度・パレットの作り方まで、UIの色を「数値と根拠」で語れるようになる9個を、一次ソースに紐づけて解説します。

読了目安 約10分（日本語の読速 約400〜600字/分を前提）／出典はすべて台帳ID付き

この記事を読み終えるころには、世の中のUIの色が「読める／読めない」で見える目に変わります。感覚で選んでいた色を、「本文は背景と4.5:1以上」「押してほしい所にアクセント色を1色」「色だけで状態を伝えない」のように、根拠のある初期値で語れるようになります。

大事なのは、断定を鵜呑みにしないこと。「鮮やかで目立つ色ほど良い」「正解の配色がある」という思い込みには、実在DSの中に反例があります。だからこの記事も余白編と同じく、一次ソースが書くこと（事実）と、実務での使い方（解釈）を、色で分けて示します。

事実＝WCAGやApple・Material・GOV.UK・Uber Base など一次ソースの記述を、原文に忠実に言い換えたもの。末尾に出典チップ（台帳ID＋URL）が付きます。
解釈＝その事実を、初心者が実務でどう使えばよいかに落とした推奨。断定は避け「原則」「定番」で示します。

01

色は"意味"を持たせる道具

色を1色ずつ好みで選ばない。まず「この色は何の役割か——本文か、押してほしいアクションか、状態か」を決めてから色を割り当てる。

押してほしい所に置く"アクション色"も役割のひとつ。色は飾りでなく、意味とアクションの目印。

Material 3 は色を「ロール（役割）」として定義します。primary（高強調）／secondary・tertiary（強調の階層）／surface（背景）／"on-"接頭辞の色（その親色の上に載る文字・アイコン用）を、UIの用途ごとに割り当て、トークンとして実装します。Uber Base も色をセマンティックなトークン（contentPrimary など）で一元管理しています。 S-17 · Material 3 Q-04 · Uber Base だから色は「飾り」ではなく「役割を運ぶ道具」です。まず「この色は何の役割か——本文か、アクセントか、状態か」を言えるようにするのが第一歩。1色ずつ好みで選ぶのをやめ、役割に色を割り当てる発想に切り替えましょう。

色は "paint-by-number（数字塗り絵）の番号のようなもの" だと M3 は言います——番号（役割）が先に決まり、色は後から入る。洗練された画面ほど、色は個別でなく体系的に決められています（洗練-05／Stripe A-03）。

02

コントラスト比という物差し

本文の文字色は、背景と4.5:1以上のコントラストにする。

大きな文字（18pt以上、または太字14pt以上）は3:1以上。おしゃれに見える薄いグレー文字は避ける。

WCAG 2.2 の SC 1.4.3 は、通常テキストは背景と4.5:1以上、大きな文字（18pt以上、または太字14pt以上）は3:1以上を求めます。より広く読める強化基準 AAA（SC 1.4.6）は7:1／4.5:1です。計算値は丸めてはならず、原文いわく "4.499:1 would not meet the 4.5:1 threshold"（4.499は4.5を満たさない）とされています。 F-01 · WCAG 2.2 F-02 · WCAG 2.2 本文は4.5:1以上を初期値に。おしゃれに見える薄いグレー文字は、たいていこの線を割っています。余裕があれば7:1を狙う——「必須は4.5:1、上級は7:1」の2段構えで考えると、丸めの誘惑に負けずに済みます。

コントラスト比は、前景色と背景色の明るさの差を1つの数字にした物差しで、感覚の「見やすい／見にくい」を共有できる数値に翻訳します。下の図には、この記事自身の本文・リンクの実測比も載せました——教えている基準をページ自身も満たしているか、数字で確かめられます。

03

非テキストのコントラスト

入力欄の枠・アイコン・状態表示は、隣り合う色と3:1以上のコントラストにする。

"見えている必要がある"線は3:1が対象。装飾だけの罫線は対象外なので、そこは自由に淡くしてよい。

WCAG 2.2 の SC 1.4.11 は、UI部品の識別に必要な視覚情報（枠線・アイコン・状態表示）も、隣接する色と3:1以上のコントラストを求めます（非アクティブな部品は対象外）。Uber Base はボーダーを黒のアルファ階調（hsla(0,0%,0%,0.04〜0.24)）で段階的に持ち、階層を作っています。 F-03 · WCAG 2.2 Q-11 · Uber Base 文字だけでなく「枠が見えるか」も色の設計対象です。薄すぎる入力欄の枠は、"ある"ように見えて機能していません。おしゃれに見せようと枠を淡くしすぎると、どこが入力欄なのか分からなくなる——この落とし穴は初心者がとくにハマりがちです。

ボタンの輪郭・アイコン・グラフの線など、情報を伝えるために"見えている必要がある"ものは3:1の対象。装飾だけの罫線は対象外なので、そこは自由に淡くできます。

04

色だけに頼らない

エラーやリンクを「色だけ」で示さない。色＋アイコン＋文言で、手がかりを二重・三重にする。

白黒にしても意味が伝わるか、を基準にする。色は補強、文言が本体。

WCAG 2.2 の SC 1.4.1（Use of Color）は「色を、情報・操作・状態・要素の区別を伝える"唯一の"視覚手段にしてはならない」と求めます。Apple HIG も "Avoid relying solely on color..." とし、テキストラベルやグリフ形状など色以外の手段でも同じ情報を伝えるよう促しています。 F-13 · WCAG 2.2 F-14 · Apple HIG エラーを赤"だけ"で示さないこと。赤＋アイコン（⚠）＋文言のように、手がかりを二重・三重にします。「色覚特性のある人にも、白黒印刷でも伝わるか」を基準にすると外しません。これはコントラスト比（項目2・3）とは別の、独立した達成基準です。

色の見え方には個人差があり、赤と緑の区別がつきにくい人もいます。色は情報を"補強"する道具であって、"唯一"の伝達手段にはしない——これを守るだけで、UIは多くの人に届くようになります。

05

無彩色で階層をつくる

有彩色を足す前に、黒〜グレーの3段階（#000000 → #4B4B4B → #5E5E5E 相当）で見出し・本文・補足を分ける。

薄いグレー（#A6A6A6 相当）は、無効・プレースホルダ表示だけに使う。読ませる文字には使わない。

Uber Base はグレースケールだけで文字の階層を作ります。本文・見出し＝#000000、補助テキスト＝#4B4B4B、キャプション＝#5E5E5E。プレースホルダ／無効（disabled）＝#A6A6A6 は背景白に対して4.5:1を満たしませんが、これは F-01 の「無効な部品は対象外」の例外に当たります。 Q-04 · Uber Base F-01 · WCAG 2.2 有彩色を使う前に、まず無彩色の濃淡だけで階層は作れます。濃さの差が、そのまま重要度の差になります。ただし #A6A6A6 のような薄いグレーは "無効表示" にだけ許される例外で、読ませたい文字には使わない——ここが色の落とし穴です（項目2の"薄いグレー文字"と地続き）。

まず濃淡でどこまでやれるか試し、そのあとで初めてアクセント（項目6）を1色足す——この順番だと画面が締まって見えます。「階層をつくる＝色を増やす」ではありません。

06

アクションに色を置く — だから1色に絞る

押してほしいボタン・リンクにだけアクセント色を1色置く。それ以外は無彩色でそろえる。

有彩色の第一の仕事は「ここを押す・ここが大事」を示すこと。目立たせたいからと、色数を増やさない。

色を使うことは、UIの基本動作です。Apple HIG は肯定形で "If you apply color, reserve it for elements that truly benefit from emphasis, such as status indicators or primary actions."（色を使うなら、ステータス表示やプライマリアクションなど、強調が本当に効く要素のために取っておく）と述べ、Material 3 も primary ロールを "High-emphasis fills, texts, and icons"（高強調）と定義します。実際 Uber Base のアクセント blue600 ＝ #276EF1 は1色で、リンク・フォーカスに限定されます。実務の観察でも「画面内の有彩色をプライマリCTAの1色に制限し、他を均一にするから、単色のCTAが唯一の焦点として際立つ」とされます。 F-14 · Apple HIG S-17 · Material 3 Q-05 · Uber Base だから有彩色の第一の仕事は「ここを押す・ここが大事」を示すこと。押してほしい所（CTA・リンク・状態）にアクセント1色を絞ると、視線が迷いません。逆に色数を増やすほど、どれも目立たなくなる——「目立たせたいから増やす」は逆効果です。この記事自身も、アクセントを1色（紫）に絞っています。

「色を絞る」と「色でアクションを示す」は同じことの表裏です。周りをグレースケールで静かにそろえるからこそ、たった1色のアクセントが「ここを押せる」と強く語ります（洗練-05／Stripe A-03）。原色をあちこちに置くと、どれが操作できる所か読めなくなります。

07

意味色（成功・警告・エラー）

成功＝緑・警告＝黄・エラー＝赤を、自分で発明せず、実在DSの値から借りる。

淡い背景＋濃い枠・文字のセットで持ち、色だけにせず文言も添える。

Uber Base の意味色は positive ＝ green600 #0E8345／warning ＝ yellow600 #9F6402／negative（error）＝ red600 #DE1135、エラーの淡い背景 ＝ #FFF0EE です。フォームのエラー時は、入力欄の枠と文字を赤（#DE1135）にし、背景を白に切り替える運用が定義されています。 Q-05 · Uber Base Q-07 · Uber Base Q-08 · Uber Base 成功＝緑・警告＝黄・エラー＝赤は、多くの人が共有する初期値です。自分で意味色を発明せず、実在DSの値を借りると外しません。ただし項目4のとおり、色だけでなく文言も添えること——意味色は"色の共通語"であって、単独で意味を背負わせる道具ではありません。

意味色のコツは「淡い背景＋濃い文字・枠」のセットで持つこと。Base のエラーも淡背景（#FFF0EE）に濃い赤（#DE1135）でコントラストを確保します。背景まで原色にすると文字が読めなくなります。

08

パレットの作り方（トーナル）

色を1つずつ当てず、明度のスケール（トーン0→100）を1本決めて、その中から役割ごとに取り出す。

暗いトーンは文字（on-色）、明るいトーンは背景（surface）に割り当てる。

Material 3 は、1つの色相の明度（トーン）0〜100 からなる「トーナルパレット」を持ちます。公式トークンにも primary0〜primary100（0/10/20/…/90/95/99/100 の刻み）や neutral0〜neutral100 が定義され、この明度スケールから on-色・surface などの役割色を体系的に取り出します。Stripe も知覚均等な色空間で色システムを設計したと述べています。 S-18 · Material 3 S-17 · Material 3 配色は「良い色を1つずつ当てる」より「明度のスケールを1本決めて、その中から役割ごとに取り出す」のが堅牢です。余白の8pxグリッドと同じ"スケール思考"が、色にもあります。恣意的に色を足すのではなく、決めたトーンの中から選ぶ——これが再現性のある配色の作り方です。

下の図は無彩色（neutral）のトーンランプの例です。暗いトーンを文字に、明るいトーンを背景に取り出す——色相が変わっても、1本のスケールを用意し役割ごとにトーンを割り当てる発想は同じです。

09

「唯一の正解」ではない（反例と方針比較）

配色を丸ごと真似る前に、役割と基準（コントラスト・意味）を先に決めて、その中から色を選ぶ。

「本文は純黒が正解」のような唯一解を探さない。実在DSでも方針は割れる、と知っておく。

実在のデザインシステムでは、本文色の"純黒"すら割れています。Uber Base の本文色は #000000 ですが、GOV.UK の本文色は #0b0c0c（わずかに濃い灰）です。基調も、Base は白黒中心、GOV.UK はリンク #1a65a6・ブランド #1d70b8 の青中心と、方針が異なります。ただし GOV.UK も WCAG 2.2 の SC 1.4.3（コントラスト最小）AA 準拠を明記しています。 Q-04 · Uber Base F-15 · GOV.UK F-01 · WCAG 2.2
反例

だから「鮮やかで目立つ色ほど良い」「唯一の正解の配色がある」は誤りです。本文＝純黒 #000 でさえ、Base（#000000）と GOV.UK（#0b0c0c）で割れています。本質は色そのものより「役割と基準（コントラスト・意味）を決め、その中で選ぶ」こと。サービスによって基調の方針は違っても、コントラスト（項目2）という物差しは共通して守られています。

ここが、事実と解釈を分ける練習の総仕上げです。「純黒が正しい」「青が正しい」ではなく、"自分のパレットの役割と基準を決めて、その中の値を使う"こと。Base でも GOV.UK でも、決めて守れば品質は保てます。正解を1つ覚えるより、「なぜその色なのか」を観察できる目のほうが、長く役立ちます。

実在のDSを覗くと「文脈で正解が変わる」ことが分かります。次にUIを見たとき、「本文は純黒か少し灰か」「アクセントは何色に絞られているか」と観察してみてください。色を疑えるようになったら、配色の解像度はもう一段上がっています。

まとめ：色は根拠で語れる

  • 色は"役割"を運ぶ道具。まず「この色は何の役割か」を言う（項目1）。
  • 本文は背景と4.5:1以上、非テキストは3:1以上。丸めない（項目2・3）。
  • 色だけで情報を伝えない。色＋アイコン＋文言で二重化（項目4）。
  • まず無彩色で階層を作り、有彩色はアクション（CTA・リンク）に1色だけ置く（項目5・6）。
  • 成功＝緑・警告＝黄・エラー＝赤は借りてくる。淡背景＋濃い枠でセットに（項目7）。
  • 色は"スケール"で持つ。基調に唯一の正解はないが、コントラストは共通で守る（項目8・9）。

数値はすべて一次ソース（WCAG・Apple・Material・GOV.UK・Uber Base、および観察としての Stripe 公式記事）に紐づけて管理しています。

理解度チェック — 5問

選択肢を選ぶと、正誤と解説が出ます。採点も保存もしません。何度でも選び直せます。（JavaScriptが無効な場合は、各項目のセクションを参照してください。）

Q1. WCAG（AA）が、通常サイズの本文テキストに求める最低コントラスト比は？

正解は 4.5:1。通常テキストは背景と4.5:1以上が最低ライン。3:1は「大きな文字」の基準、7:1はより広く読める強化基準（AAA）です。計算値は丸めません。

3:1＝大きな文字（18pt/太字14pt）の基準／7:1＝AAA（強化）／2:1＝不足で不合格。

F-01 · WCAG 2.2 F-02 · WCAG 2.2 → 項目2「コントラスト比という物差し」へ

Q2. 入力エラーの伝え方として、より適切なのはどれ？

正解は 赤色＋アイコン＋文言。色は情報を伝える"唯一の"手段にしない、というのが WCAG 1.4.1 と Apple HIG の求めるところ。色覚特性のある人や白黒表示でも伝わるよう、色以外の手がかりを添えます。

「赤だけ」は色を抜くと違いが消える／背景を派手にするとコントラストが崩れ本文が読めない／太字だけでは"エラー"の意味が伝わりにくい。

F-13 · WCAG 2.2 F-14 · Apple HIG → 項目4「色だけに頼らない」へ

Q3. 薄いグレー #A6A6A6（背景白に対し4.5:1未満）を使ってよいのは？

正解は 無効表示などの例外にだけ。#A6A6A6 は白背景に対して約2.4:1で4.5:1を満たしません。WCAG は「無効な部品は対象外」とするので、無効・プレースホルダ表示にだけ許される例外です。読ませたい文字には使いません。

本文・見出しに使うと基準割れ。読ませる文字は #5E5E5E より濃いトーンにします。

Q-04 · Uber Base F-01 · WCAG 2.2 → 項目5「無彩色で階層をつくる」へ

Q4. 有彩色（色みのある色）の使い方の初期値として、適切なのは？

正解は アクセントを1色に絞る。Uber Base のアクセントは #276EF1 の1色。周囲を無彩色で静かにそろえるからこそ、1色のアクセントが唯一の焦点として際立ちます（洗練-05 の観察）。色数を増やすほど、どれも目立たなくなります。

色を増やす・原色を多用すると焦点が分散。好きな色を都度足すと役割がぶつかります。

Q-05 · Uber Base → 項目6「アクションに色を置く — だから1色に絞る」へ

Q5. 「本文の色は純黒 #000000 が唯一の正解だ」——これは？

正解は 誤り。Uber Base の本文は #000000、GOV.UK は #0b0c0c と、実在DSでも割れています。唯一の正解の配色はなく、本質は「役割と基準（コントラスト・意味）を決め、その中で選ぶ」こと。ただし、どちらもコントラスト基準は共通して守っています。

「黒を使わない」「濃いほど良い」も極端。大事なのは基準を満たす範囲で文脈に合わせて選ぶこと。

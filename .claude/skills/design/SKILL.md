# Design Implementation Workflow

## 概要

Figmaデザインを分析し、デザインシステムに沿ってコンポーネントを実装するワークフロー。

## 呼び出し方

- `/design [Figma URL]` - 新しいデザインを分析
- `/design analyze [Figma URL]` - 分析のみ（実装しない）
- `/design implement [コンポーネント名]` - ドキュメントに従って実装
- `/design token [Figma URL]` - トークン抽出のみ

---

## ワークフロー

### Phase 1: 分析（analyze）

1. **デザインシステム確認**
   - `.claude/design-system/README.md` を読む
   - 既存トークン・コンポーネントを把握

1.5. **このFigmaデータは既存タイポグラフィルールに従うか、上書きするかを最初に確認する**
   - `.ds-h1`〜`.ds-h5`等のセマンティッククラスは見出しを全て`font-weight:700`固定で定義しているが、Figmaのデザイン（特にリニューアル・別デザイナー案件）が`font-medium`(500)等の異なるweightを使っている場合がある
   - **勝手に既存ルールに寄せない。勝手にFigmaを優先して既存ルールを無視しない。** 実装前に必ずユーザーへ「今回のFigmaは既存デザインシステムのタイポグラフィルールに従うか、それともFigmaの実測値をそのまま優先するか」を確認する
   - 確認が取れたら、その回答をこのファイルの「対応するFigmaファイル」表、または該当プロジェクトの `docs/` に明記し、以後のコンポーネント実装で毎回参照する

2. **トークン・マッピング決定表（要素の種別ごとに判断基準が異なる）**
   Figma実測値をこのプロジェクトの配線実態に応じて振り分ける。「トークンを使えarbitrary禁止」は色にしか一律適用できない（spacing/typographyの設計トークンはTailwindに配線されておらず、既存コンポーネントもarbitrary値を多用している実態がある）。

   | 種別 | 変換ルール |
   |---|---|
   | **色** | 必ず配線済みトークン（`text-text-primary`, `bg-muted-custom`等）を使う。生hex禁止。トークンに無い色のみユーザー確認の上 arbitrary |
   | **spacing** | Tailwindの`p-*/m-*/gap-*`は4px基準（`--spacing:0.25rem`）で自動生成されており、このプロジェクトの `--s-*` 設計トークンと1:1で一致するよう設計されている（`.claude/design-system/colors_and_type.css`参照）。**4pxの倍数ならTailwindの数値クラスをそのまま「公式の余白トークン」として使う**（`16px`→`p-4`、`24px`→`gap-6`等）。4pxの倍数でない値のみ arbitrary（`gap-[27px]`等） |
   | **radius / shadow** | Tailwind標準クラスで一致するものがあれば使う。無ければFigmaの値をそのままarbitraryで（丸め禁止） |
   | **typography** | 1.5で確認した方針に従う。既存ルール優先なら`.ds-*`、Figma優先ならFigma実測のfont-family/weight/size/line-height/trackingをそのままarbitraryで再現する |

2. **Figma分析（スクリーンショットは必ず取得する）**
   - `get_design_context` でデザイン情報取得。**`excludeScreenshot: true` は使わない**（コンテキスト節約のために省略すると、Figma側の見た目を一度も見ないままコードの数値だけで実装することになり、実際に大きなスタイル崩れを見逃した事例がある）
   - `get_screenshot` で追加のビジュアル確認（必要に応じて）
   - `get_variable_defs` でFigma Variables取得

3. **スタイル抽出チェックリスト（テキスト要素は1つずつ、漏れなく）**
   コンポーネント内の**全てのテキスト要素**について、以下を表にして書き出してから実装に入る。「タイトルだけ確認して他要素(ラベル・説明文・ボタン文言)を見落とす」というつまみ食い的チェックで実際に複数のfont-weight不一致を見逃した反省による。

   | 要素 | font-family | weight | size | line-height | tracking | 色 |
   |---|---|---|---|---|---|---|
   | 見出し | M PLUS 1 | Medium(500) | 32px | 44.8px | 1.6px | #141419 |
   | 本文 | Noto Sans JP | Regular(400) | 16px | 28.8px | 0.8px | #141419 |

   - Figmaが `font-normal`/`font-medium` と指定している場合、**既存コンポーネントとの「一貫性」を理由に `font-bold` 等へ勝手に寄せない**。寄せたい場合は実装前にユーザーへ提案し確認を取る
   - `border-black/20` と `border-black/[0.12]` のように、コード上は似て見えても実際の見た目差が大きい微妙な透明度・色値も見落とさず、Figmaの数値をそのまま使う

4. **分析レポート作成**
   以下の形式でユーザーに報告：

```markdown
## 分析レポート

### 基本情報
- **Figma node-id**: `xxx-xxx`
- **コンポーネント名（提案）**: XxxCard

### 構造
```
[構造図]
```

### 検出したスタイル（上記チェックリストの表を含める）
- 背景色: #XXX → `bg-xxx`（既存）/ 新規追加必要
- フォント: 16px semibold → `text-base font-semibold`
- 余白: 16px → `p-4`

### 既存デザインシステムとの対応
- [一致するトークン]
- [新規追加が必要なトークン]

### 質問事項
- [ユーザーに確認したいこと]
```

5. **ユーザー確認待ち**
   - 命名の確認
   - 新規トークンの確認
   - 実装方針の確認

### Phase 1.5: レスポンシブ設計

Figmaはデスクトップ1枚絵のことが多いため、モバイル/タブレットのレイアウトは設計判断が必要になる。判断を都度その場で決めず、以下の型に沿う。

**ブレークポイントの責務**（このプロジェクトは `sm:640px` / `md:768px` / `lg:1024px`）
- 既存コンポーネントは `sm:` を主ブレークにしている（例: `EyecatchSection` の `sm:flex-row`）。**原則 base→sm の2段**で組み、3段以上必要な密度の時だけ `md`/`lg` を足す（ブレーク乱立は検証コストを増やすだけ）
- `lg:`（1024px〜）=Figmaのpx値がそのまま効く基準幅

**デスクトップpx→モバイル値の導出ルール**
1. 固定px幅要素（カード等）: モバイルは `w-full` に開放。Figmaの固定幅はデスクトップ基準でのみ再現する
2. 横並びグリッド: 列数を段階的に減らす（3列→`md:`2列→base1列）。gutterもブレークごとに縮小可
3. フォントサイズ: 見出し等は base値/`sm:`値の2段指定を第一選択。`clamp()`は連続スケールが明確に必要な大型見出しに限定し、乱用しない（テストしづらく事故の温床）
4. 画像/アスペクト比: `aspect-[W/H]`（Figma実寸比）＋`w-full`で高さを内容から導出する。**パーセンテージ高さ（`h-[80%]`等）で近似しない**（Phase 3参照）

### Phase 2: ドキュメント化

ユーザー確認後：

1. **トークン追加**（必要な場合）
   - `.claude/design-system/tokens/` を更新

2. **コンポーネント仕様作成**
   - `.claude/design-system/components/[component].md` を作成
   - テンプレート: `.claude/design-system/components/_template.md`

3. **Figmaマッピング更新**
   - `.claude/design-system/figma/node-mapping.md` に追加

### Phase 3: 実装（implement）

1. **仕様参照**
   - `.claude/design-system/components/[component].md` を読む

2. **既存の共有コンポーネントに手を入れる場合は影響範囲を先に確認**
   - `grep`等で「このコンポーネントを使っている箇所」を全て洗い出す
   - 1つのブロックの要件（例: ホバー時の背景色を付けたい）のためだけに、他ブロックでも使われているコンポーネントへ無条件に変更（`padding`追加など）を加えない
   - 実例: あるブロックのホバー要件でカードに `p-3` を無条件追加した結果、同じカードを使う別ブロックの余白が全て12px縮んでズレた。パディングでホバー領域を作る場合は `-m-3 p-3`（負のmargin相殺）のように、既存レイアウトへの影響を打ち消す実装にする

3. **CSS実行時の罠（コードの数値比較では見抜けない）を防ぐアンチパターン表**

   | 症状/罠 | 禁止 | 正解 |
   |---|---|---|
   | %高さが解決されない | `h-[80%]`（flex+aspect-ratioの文脈で親高さ未確定） | Figmaの入れ子構造（パディング＋aspect比ラッパー）をそのまま再現。サイズは`aspect-[W/H]`＋`w-full`で内容から導出する |
   | 共有コンポーネントへの副作用 | 共有カードに`padding`を無条件追加 | ホバー領域等は`-m-3 p-3`（負margin相殺）でレイアウト影響を打ち消す。または variant prop 化 |
   | flex子のはみ出し | `flex-1`のみ（`min-width:auto`で溢れる） | `flex-1 min-w-0` |
   | line-heightの丸め | `leading-7`(28px)でFigmaの28.8pxを近似 | `leading-[1.8]`等の比率、または`leading-[28.8px]`で実測再現 |
   | transitionが効かない | 素の`transition`（Tailwind v4はデフォルト実質0ms） | プロジェクトの`--default-transition-duration:150ms`設定を前提に確認。効かなければduration明示 |

4. **コンポーネント実装**
   - 仕様に従って `src/components/` に実装
   - トークンを使用（ハードコード禁止）
   - Phase 1 のスタイル抽出チェックリストと1つずつ突き合わせながら実装する（あとでまとめて確認、ではなく実装しながら）

5. **視覚的な検証を必ず行う（コードの数値比較だけで「確認済み」と言わない）**
   - Figmaの生成コードとTailwindクラスの数値を読み比べるだけでは、CSSの実行時の挙動（パーセンテージ高さの解決失敗、共有コンポーネントへの副作用など）は原理的に発見できない
   - 実装後、可能であれば `mcp__claude-in-chrome__*` 系ツールで実際のレンダリング結果をスクリーンショットし、Figmaのスクリーンショットと並べて突き合わせる
   - ブラウザ確認ができない環境の場合は、**その制約を正直にユーザーへ伝えた上で**、ユーザーにスクリーンショットの提供を依頼し、Figma側のスクリーンショットと突き合わせてから「確認済み」と報告する。ブラウザ確認なしに「数値は合っているので大丈夫です」と断定しない

6. **粒度は「コンポーネント単位」→「ブロック単位」の2段階。一気にまとめて読み込み・実装しない**
   - 1ブロックは通常、複数のコンポーネント（見出し・カード・ボタン等）の組み合わせでできている。Figmaのデータを一気に全部読み込んで一括で実装する、というやり方はしない
   - まず**コンポーネント単位**で1つずつ実装する: そのコンポーネントのFigmaノードだけを取得 → スタイル抽出チェックリストを作る → 実装 → そのコンポーネント単体で視覚的に突き合わせる
   - 全コンポーネントが揃ったら、次に**ブロック単位**で組み立てる: コンポーネントを並べて配置・余白を組む → ブロック全体で改めて視覚的に突き合わせる（コンポーネント単体では見えない、間隔やセクション全体の余白のズレはここで確認する）
   - 複数ブロックをまたいでまとめて実装依頼・確認せず、常に「1コンポーネント→確認」「1ブロック→確認」のサイクルを守る。まとめて進めると、どの変更が原因でスタイルが崩れたのか特定できなくなる

7. **プレビューページ作成**（任意）
   - `/dev/[component]` ページを作成

8. **完了報告**

```markdown
## 実装完了

### 作成ファイル
- `src/components/xxx/Xxx.tsx`
- `src/pages/dev/XxxPreview.tsx`（プレビュー）

### 使用トークン
- 色: `bg-card`, `text-foreground`
- フォント: `text-lg font-semibold`

### スタイル突合結果
- Phase 1 チェックリストの各項目とコードの対応（一致 / 意図的な差異とその理由）

### 視覚確認の状況
- スクリーンショット突合を行ったか、行えなかった場合はその理由

### 確認方法
http://localhost:5173/dev/xxx
```

## 重要ルール

### 必ず守ること

1. **分析結果は必ずユーザーに報告**
   - 勝手に命名しない
   - 勝手にトークン追加しない

2. **デザインシステム参照**
   - 既存トークンを最大限活用
   - 新規追加はユーザー承認後

3. **ドキュメント先行**
   - 実装前にコンポーネント仕様を作成
   - Figmaマッピングを更新

4. **一貫性の維持**
   - 同じFigmaコンポーネントは同じ実装
   - `node-mapping.md` で管理

5. **Figmaの値をそのまま使う**
   - font-weight/size/line-height/tracking/色は、既存コンポーネントとの「一貫性」を理由に別の値へ勝手に寄せない
   - 寄せたい場合は実装前にユーザーへ提案し確認を取ってから変更する
   - 特にタイポグラフィは、新しいFigmaデータが既存の`.ds-*`セマンティッククラス（見出し全てbold固定）と異なるweightを使っている場合がある。**Phase 1.5相当の確認（既存ルールに従うか上書きするか）を必ず実装前に取る**

6. **視覚的検証を省略しない**
   - コードレベルの数値比較だけで「Figma通りです」と報告しない
   - ブラウザ確認ができない場合はその旨を正直に開示する

7. **レイアウト基準は既存の`.container`（唯一の幅基準）**
   - `globals.css`に既存の`.container`（max-width 640/768/1024/1280/1400, padding 2rem）がある。新規セクションは自前のmax-widthを発明せず、これを使う
   - Figmaのコンテンツ最大幅は`container`の`1280`/`1400`にマッピングする
   - 左右paddingはモバイル`px-6`〜`px-5`、`lg:`でcontainerの2remに収束させる。セクションごとに独自paddingを発明しない

8. **spacingはTailwindの数値クラスを公式トークンとして扱う**
   - `--s-*`設計トークンはTailwindの4px基準スケールと1:1で一致するよう設計されている（`.claude/design-system/colors_and_type.css`参照）
   - Figma実測値が4pxの倍数なら、対応するTailwind数値クラス（`p-4`, `gap-6`等）をそのまま使う。4pxの倍数でない値のみarbitrary

### やらないこと

- ハードコードで色・サイズを指定
- デザインシステムを無視した実装
- ドキュメント更新を忘れる
- `excludeScreenshot: true` でFigmaのスクリーンショットを省略する
- 1つのブロックの要件のためだけに、他ブロックと共有しているコンポーネントを無条件に変更する
- パーセンテージ指定でサイズを近似する（Figmaの入れ子構造を再現できる場合はそちらを優先）
